# RepoScope Hy3：场景、方法、实验与能力边界

## 1. 场景选择

目标用户是需要决定是否引入某个开源项目的开发者、架构师和技术负责人。他们面对的输入
通常同时包含代码、README、依赖、CI、测试和许可证；最终建议没有唯一标准答案，却必须能
经受追问：“这条结论依据什么？”

传统仓库摘要可以压缩信息，但容易把文件存在、文档承诺和实际验证混为一谈。大模型的必要
性在于跨文件整合非结构化证据、识别矛盾、形成针对具体采用目标的条件化建议；确定性程序的
必要性在于验证路径、行号和原文，防止模型同时扮演作者与事实来源。

## 2. 解决方案

RepoScope 采用五段式流程：

1. 只接受白名单公开 HTTPS Git 仓库，并固定 commit；
2. 有界采集项目元数据、关键源码、测试与 CI 文档，生成带哈希的证据清单；
3. Hy3 根据版本化 JSON Schema 输出结论、风险、建议、未知项与逐条引用；
4. 确定性评估器检查覆盖率、文件、行号、原文、可执行性和格式；
5. 可选 Hy3 语义评审检查事实准确、证据蕴含、重大风险遗漏和清晰度。

确定性硬门槛优先于语义总分：无论语言多流畅，只要无效引用超过 20%，或引文落地率低于
60%，总分最高为 59。

## 3. 评估设计依据

开放式报告的主要风险不是文风差，而是关键判断无法审计。因此 v1.0 将 65% 权重分配给
证据覆盖、引用有效和引文落地；不确定性、建议可执行性与格式合规共同占 35%。详细 0-4
锚点、权重和语义量表见 `docs/EVALUATION.md`。

评估方式是混合式，而不是单一 LLM-as-judge：

- 规则层适合完全可复现的路径、范围、原文与 Schema 校验；
- Hy3 语义层适合判定引用是否真正支持结论、是否存在重大遗漏；
- 双人盲标适合校准语义边界并识别同模型生成与评审的相关偏差。

## 4. 样本与覆盖

当前可复现实验包含 84 个合成样本：24 个仓库家族，每个家族具有好、中、差三档报告；
另有 12 个对抗报告，覆盖伪造路径、真实路径配错误引文、专业术语与篇幅堆砌、过度自信和
未知项缺失。语言标签覆盖 Python、TypeScript、Java、Go、Rust 与 C++。

样本通过 `scripts/generate_benchmark.py` 生成，逐条输入和预期档位保存在
`datasets/benchmark/cases.jsonl`。它们用于验证评估逻辑，不作为真实项目分布的替代品。

## 5. 有效性验证结果

执行 `scripts/run_experiments.py` 得到：

- 24/24 组报告满足好分数 > 中分数 > 差分数；
- 构造质量档位与得分 Spearman 相关系数为 1.0000；
- 好、中、差平均分为 100.0、61.5、18.5；
- 12/12 对抗样本均以低于 60 分且触发硬门槛的方式被拒绝；
- 每个样本重复 5 次，确定性评分最大标准差为 0。

这两项实验分别覆盖任务要求中的判别力和同一输出重复评估的一致性。它们证明规则实现与
构造目标一致，但不证明真人评分一致，也不证明真实 Hy3 输出达到相同分布。

### 5.1 真实 Hy3 自检案例

以 RepoScope 自身 commit `ed167494e5c6107b56a110fe65f3d49ee72833e7` 作为冻结快照，
在 80,000 字符证据预算下完成一次真实 TokenHub Hy3 调用：

- 报告生成耗时 20.523 秒，包含 5 条关键结论、3 项风险与 12 个引用；
- 规则评估器 v1.1 验证 12/12 路径、行号和引文，得分 100，无硬门槛失败；
- 三次 Hy3 语义复评中，事实准确和证据蕴含均为 4.0，风险完整性均为 3.0，专业清晰度
  均为 4.0；各维度总体标准差均为 0；
- 三次语义复评耗时分别为 14.698、15.016 和 13.252 秒。

该案例的 manifest、原始报告、规则结果、三份语义结果和汇总均保存在
`results/live/ed167494e5c6/`。它证明真实调用链已贯通，但样本量为 1，且生成与语义评审使用
同一模型家族，不能替代跨仓库实验和真人标注。

### 5.2 真实外部仓库浏览器端到端案例

针对 `pypa/sampleproject` commit `621e4974ca25`，通过实际浏览器完成仓库导入、Hy3 生成、
规则评分与 Hy3 语义复核。首次运行发现采集器遗漏 `LICENSE.txt`，导致生成与复核共享错误
前提；修复并加回归测试后，以同一 commit 重新运行：规则层得到 90/A，语义层得到事实 3、
蕴含 3、风险完整 3、清晰度 4。语义层还识别到一个“结论有快照信号支持、但引用正文不支持”
的部分支持案例。完整过程与截图见 `reports/live_ui_e2e.md`。

## 6. 典型失败模式

### 6.1 引用幻觉

报告给出看似具体的文件和行号，但文件不存在。仅使用 LLM 判断可能被“具体感”误导；路径
检查会直接将其判为无效。

### 6.2 引用与结论错配

引用真实 README 安装行，却宣称数千个生产测试通过。文件存在不等于证据蕴含，因而需要
引文原文检查和语义评审两个层次。

### 6.3 证据缺失被写成否定事实

“未找到 SECURITY.md”只能说明快照中未发现该文件，不能推出项目没有漏洞响应渠道。良好
报告会将外部流程、维护者响应时间等内容放入 unknowns。

### 6.4 语言质量劫持总分

对抗样本重复企业级、全面、专业等措辞，但引用仍为伪造。当前规则层不对篇幅和术语加分，
因此攻击不会改善得分。

### 6.5 同模型偏差

默认情况下 Hy3 同时承担生成和可选语义评审，可能共享偏好与遗漏。系统不允许语义得分覆盖
确定性硬门槛，并把真人双盲标注保留为最终校准来源。

## 7. 模型能力边界

Hy3 适合跨多份文档整理证据、生成结构化结论、解释采用条件并发现语义层面的矛盾。它不能
仅凭静态快照证明测试实际通过、许可证适用于某个具体法域、系统没有漏洞或维护者未来会及时
响应。RepoScope 也不是完整的 SAST、依赖漏洞扫描或法律意见系统。
